# 13 — Support Views (404 & Error Pages)

Status: Implemented
Depends on: [05-base-layout](./05-base-layout.md)

## Goal

Right now, both a missing route and a runtime error fall through to Next.js's bare default pages: unstyled, outside `PageShell`, no locale awareness, no nav/footer, no way back into the site. This spec adds proper 404 and runtime-error views so a broken link or a thrown error still lands the visitor somewhere on-brand and navigable, not a dead end — the CV/portfolio angle from spec 00 means this is also public-facing craft, not just an edge case.

## Scope

- **`src/app/[locale]/not-found.tsx`** (Server Component): the 404 shown for any unmatched path _under_ a valid locale (e.g. `/en/nonexistent`). Reached via a new `src/app/[locale]/[...rest]/page.tsx` catch-all (see Implementation notes — required for this to be reachable at all) which mounts the `[locale]` layout and calls `notFound()`. Rendered inside `[locale]/layout.tsx`, so it automatically gets `PageShell` (header/nav/footer) and the active locale's translations — same as every real page. Content: `h1` ("Page not found"/"Página no encontrada"), one line of body copy, a link back to the locale-prefixed home (`/en` or `/es`).
- **`src/app/not-found.tsx`** (Server Component): the root-level fallback for requests that never resolve to a locale segment at all — see Implementation notes for the actual trigger condition (it's narrower than the initial draft assumed). Fires _before_ a locale is established, so it can't use `next-intl` translations or `PageShell`. Bilingual-by-necessity: both EN and ES lines shown, with two links — "Home (EN)" → `/en`, "Inicio (ES)" → `/es`. Reads the incoming `Accept-Language` header (via `next/headers`' `headers()`, same signal spec 05's locale-redirect middleware already keys off for the initial `/` redirect) to decide _which_ language's line/link renders first — the other still renders directly below it, not hidden, just second. Still wrapped in the app's theme (`ThemeRegistry` from root `layout.tsx` already covers this) so it isn't unstyled, just simpler than the localized version.
- **`src/app/global-error.tsx`** (Client Component, required by Next.js convention): catches errors thrown in the _root_ layout itself — a rarer failure mode, but since a crash here means `ThemeRegistry` may itself be the thing that broke, this file can't assume the theme, MUI, or even the root `<html>`/`<body>` from `layout.tsx` are safe to rely on. Next.js requires `global-error.tsx` to render its own `<html>`/`<body>` (it fully replaces the root layout when triggered) — kept deliberately minimal: inline styles only (no MUI, no theme import), a bilingual EN/ES message plus a "Try again"/"Reintentar" button calling `reset()`. No link back to `/en`/`/es` here — if the root layout is broken, navigating back into the app isn't a meaningful recovery path; a page reload via "Try again" is.
- **`src/app/[locale]/error.tsx`** (Client Component — Next.js requires error boundaries to be client components): catches runtime errors thrown while rendering any page under a locale. Content: `h1` ("Something went wrong"/"Algo salió mal"), one line of body copy, a "Try again" button (calls the `reset()` function Next.js passes as a prop) and a link back home. Rendered inside `[locale]/layout.tsx`'s tree, so `PageShell` and translations are still available (the error boundary sits _below_ the layout, not replacing it).
- **Message files**: `messages/en.json` / `messages/es.json` get a `notFound` namespace (heading, body, home link label) and an `error` namespace (heading, body, "Try again" label) — both consumed by `[locale]/not-found.tsx` and `[locale]/error.tsx` respectively.
- **Accessibility**: both views use a real `h1` (only heading on the page, same rule as every other page); the "Try again" control is a real MUI `Button` (not a bare `div`/`onClick`); the home link is a real `next-intl` `Link` (keyboard-focusable, visible focus ring from the theme); root `not-found.tsx`'s two language links are real `<a>` tags (can't use `next-intl`'s `Link` there — no locale context yet) with clear, distinct accessible names ("Home (EN)" / "Inicio (ES)"), not two links both labeled "Home".

## Out of scope

- A dedicated visual design/illustration for the 404/error states — reuses existing typography/spacing/`PageShell` (where available), no new design tokens.
- Retry/error-reporting integration (e.g. sending caught errors to a logging service) — no such service exists yet in this project; `error.tsx`'s `reset()` button is purely client-side re-render, no telemetry.
- A custom 500/error page for the Vercel edge/build layer itself — out of scope, this spec is about React-render-time errors and unmatched routes only.

## Backend concepts

- **`not-found.tsx` vs `error.tsx` as Next.js file conventions**: `not-found.tsx` renders when code explicitly calls `notFound()` (as `[locale]/layout.tsx` already does for an invalid locale) or when no route matches at all; `error.tsx` is an automatic React error boundary Next.js wraps around the segment it lives in, catching any error thrown during rendering below it. They're triggered differently but both replace the page content while leaving anything _above_ them in the tree (layouts) still mounted — which is exactly why `[locale]/error.tsx` still shows inside `PageShell`, but the root `not-found.tsx` can't (it replaces content at a point before the locale layout — and therefore `PageShell` — ever mounts).
- **Why `error.tsx` must be a Client Component**: error boundaries rely on React's `componentDidCatch`/error-boundary lifecycle, which only exists in the client React runtime — Server Components can't catch rendering errors this way, so Next.js requires `"use client"` on every `error.tsx`.

## Decisions

1. Two-tier 404: a themed, translated, `PageShell`-wrapped one for real in-app pages (`[locale]/not-found.tsx`), and a bilingual one for the pre-locale case (`app/not-found.tsx`) — reflects the actual constraint (no locale known yet at the root) rather than trying to force one component to cover both.
2. Root 404's language ordering is informed by `Accept-Language` (reusing the same signal spec 05's middleware already reads for the `/` redirect), but never hides either language — both always render, just reordered.
3. Two error boundaries: `[locale]/error.tsx` (themed, inside `PageShell`, for errors below the locale layout) and `global-error.tsx` (bare/inline-styled, for errors in the root layout itself) — both built now rather than deferring the rarer root-level case.
4. No telemetry/error-reporting hookup — purely a UI-level catch-and-recover.
5. Draft EN/ES copy ships now for all four views (404 ×2, error ×2), flagged for Bruno's review — same precedent as specs 06/07/08's draft content.

## Implementation notes (deviations from plan)

- **A catch-all route was required for `[locale]/not-found.tsx` to ever render — this wasn't anticipated in the draft.** Without one, an unmatched path like `/en/nonexistent` never mounts anything under `[locale]` at all (no page matches, and nothing there calls `notFound()`), so Next.js falls straight through to the _root_ `app/not-found.tsx` — bypassing `PageShell`, translations, everything spec'd for the localized 404. Verified this empirically (curl + a throwaway Playwright script) before realizing the fix: added `src/app/[locale]/[...rest]/page.tsx`, a page matching any otherwise-unmatched path under a locale, whose entire body is `notFound()`. That mounts the `[locale]` layout (so `PageShell`/`NextIntlClientProvider` are in the tree) and then explicitly triggers the nearest `not-found.tsx` boundary, which is now the localized one.
- **The root `app/not-found.tsx` is reachable, but not via the URLs the draft's scope section used as examples** (`/fr/anything`, `/nonexistent`). next-intl's middleware intercepts every request the proxy matcher covers and always rewrites to a valid locale — an unrecognized locale segment like `fr` isn't treated as "invalid," it's treated as _part of the path_ and prefixed with the detected/default locale (`/fr/anything` → 307 → `/en/fr/anything`), which then resolves to the localized 404 via the catch-all above, not the root one. The root 404 is what actually renders for requests the proxy's matcher excludes entirely (`"/((?!api|_next|_vercel|.*\\..*).*)"`) — a path with a dot that isn't a real static file (`/whatever.json`) or an unmatched `/api/*` route. Verified both cases render the bilingual root 404 correctly; the verification section below reflects the real trigger condition instead of the draft's incorrect examples.
- **`app/not-found.tsx`'s home links use `component="a"` on MUI's `Button`, not `next/link`'s `Link`.** Passing `next/link`'s `Link` (a function) as `component={Link}` from this Server Component into MUI's Client Component `Button` hit the exact RSC serialization crash spec 07 documented for `next-intl`'s `Link` ("Functions cannot be passed directly to Client Components") — confirmed via a live request that 500'd with that exact message. Since these links always cross from no-locale-context into a locale prefix, they were always going to be full page loads regardless — a plain anchor via `component="a"` (a string, not a function reference) sidesteps the serialization boundary entirely and is the correct tool here regardless of the crash, not just a workaround.
- **`error.tsx` and `global-error.tsx` were verified manually (temporary deliberate `throw` in a locale page and in the root layout, checked via a throwaway Playwright script, then reverted), not via a permanent e2e test.** A route that exists solely to throw would ship as a stray dead endpoint on the live site — not worth it for a boundary that's simple enough to verify once and trust MUI/React's error-boundary contract for going forward.

## Verification

- Visiting a nonexistent path under a valid locale (e.g. `/en/nonexistent`) renders the localized 404 inside the full header/nav/footer shell, with a working link back to `/en`. Same for `/es/nonexistent` → `/es`.
- Visiting a path the proxy's matcher excludes from locale routing entirely (e.g. `/whatever.json`, `/api/nonexistent`) renders the root-level bilingual 404, with working links to both `/en` and `/es`, and the language matching the request's `Accept-Language` header rendering first.
- A deliberately-thrown error in a page component (temporary test change) is caught by `[locale]/error.tsx`, rendered inside `PageShell`, and "Try again" re-renders the segment.
- A deliberately-thrown error in the root layout (temporary test change) is caught by `global-error.tsx`, rendering its own bare `<html>`/`<body>` with a working "Try again" button.
- All four views use a single real `h1`; the "Try again" button and all links are keyboard-operable with visible focus.
- `tests-e2e/not-found.spec.ts` covers the localized 404 (both locales, including the "back to home" link) and the root bilingual 404, plus per-locale axe checks on the localized 404 (zero violations).
- `pnpm test`, `pnpm test:e2e`, `pnpm test:storybook`, `pnpm build`, `pnpm lint`, `pnpm typecheck` all pass.
